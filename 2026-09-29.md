### Key discovery — please read
Point 2 asked for "replace emitted on content change with revision incremented," and I verified this empirically (a throwaway probe script driving the real `memory_replace` tool end-to-end) before designing around it: **the primary production path for `memory_replace` does not go through `replaceSyncedMemories`'s in-place UPDATE at all.** Because both the global and project `MemoryStore`s get a mutation observer attached at `registerMemoryTool()` setup time, `executeAction`'s `!syncHandled`-gated direct-sync calls (`syncAddToSqlite`/`syncReplaceToSqlite`) never fire in normal operation. Instead, the attached observer fires `reconcileStoreScope` → `reconcileMarkdownMemoryScope` → `syncMemoryEntry` (content-identity based), which for a changed-content entry does **delete the old SQLite row and insert a fresh one** (revision reset to 0, new row id) rather than incrementing revision in place. My probe: add "original content" (row id 1, revision 0) → replace with "updated content v2" → resulting row is id 2, revision 0, not id 1/revision 1.

Given this, I instrumented both real code paths correctly:
- `memory.write` fires from `addMemory()`, which is also what `syncMemoryEntry` calls for genuinely-new content — so it covers memory_add, digest, consolidation, background, and reconcile-driven "replace" (since that's really an insert under the hood).
- `memory.replace` fires from `replaceSyncedMemories()`, the one place in the codebase that actually does an in-place UPDATE with `revision = revision + 1`. This function is real, reachable code (used whenever `!syncHandled`, e.g. a store without an attached mutation observer — mentioned as a supported scenario in existing comments about "lightweight MemoryStore test doubles"), and it's exactly what `tests/store/provenance.test.ts`'s pre-existing test (`replaceSyncedMemories keeps the stable id, increments revision...`) already exercises directly — so I tested `memory.replace` at that same layer rather than through the full `memory_replace` tool, since the full tool path doesn't reach it in the common case.

I did not change this architecture (that would be a much larger, riskier refactor outside T-UP2's scope) — only reported it, per the same stop-condition spirit as T-UP's `memory.search_result` finding.
