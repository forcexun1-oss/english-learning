### Issues

**[CRITICAL] Permanent skip-marker can be written for a session file that is still open and will receive real messages later**
File: `mac-assistant/src/session_digest.rs:384-392` (new skip logic), in combination with `pi_agent.rs:292-339` (`warmup`/`warmup_spare`), `pi_agent.rs:1473-1508` (`reset()` promotes the spare process rather than starting a new one), and `panels/agent.rs:103-116` (`agent_screen_locked` flushes only *retiring* processes — the currently-active session and the idle spare-pool session are never touched).

I verified with a sub-agent against `pi_agent_rust/src/session.rs` that a `pi` session's JSONL file is opened once (`OpenOptions::new().append(true)`) and kept for the process's whole lifetime — the header lines (`session`/`model_change`/`thinking_level_change`) written at process start and any later real `type:"message"` entries land in the *same file, same path*. There is no rotation.

Consequence: both the main active `pi` process (started by `warmup()`) and the idle spare (started by `warmup_spare()`, later promoted verbatim by `reset()` via `activate_process()`) write their session file the instant they start, before any user message. If the screen locks in that window — e.g., app just launched and the user steps away before typing anything, or a spare is sitting in the pool waiting for the next "clear" — `count_messages` correctly returns `Some(0)` for that file (it genuinely has zero messages *right now*), and the new code writes a permanent `ok:true` marker and dequeues it. Later, when the user returns and actually chats — through that *same* live process/session — real messages get appended to that *same* file, but `pending_sessions` will never look at it again because the marker already exists. That is exactly the "silent permanent loss" class of bug this whole feature exists to prevent, just reached via a legitimately-empty-at-scan-time file instead of a misclassified unreadable one.

Important nuance: this exact risk is not newly *introduced* by Task 7's logic — before this diff, the same outcome was already reachable (any successful digest child run, on any session, wrote the same unconditional `ok:true` marker regardless of content, so a still-live empty session could already be marked "digested" if a spawned child happened to process it while empty). What Task 7 changes is that this outcome is now reached far more cheaply and therefore more often: previously it required a 12-19s inference run to complete successfully; now it's a free file-read with no spawn, so a 5-session batch (`DIGEST_BATCH_MAX`) can permanently mark up to 5 live/spare sessions per lock event instead of being throttled by inference time. The brief's stated justification for the skip ("these are steady-state artifacts of the warm pool") is empirically true of the 55/246 files sampled from history, but the code has no way to distinguish a genuinely dead orphan from a currently-open live/spare session file — there is no liveness check (e.g., against `pi_agent::state()`'s current session id, or the `.jsonl.lock` sibling file the code's own comment at `:28` already knows about).

Fix suggestion: before treating `Some(0)` as skippable, exclude the currently-active session id (exposed via `pi_agent::state()` or a small accessor) and the spare-pool's session id (if it has emitted one yet) from the skip path — or more robustly, check for a `.jsonl.lock` sibling / any signal that the file is still owned by a running process, and only apply the permanent skip-marker to files whose owning process is confirmed gone. This is arguably a Task 5 architectural fix rather than a Task 7 one, but since Task 7 is what makes it cheap to hit at scale, it should not ship without at least a targeted follow-up task, and the risk should be logged in "已知风险"/known-risks rather than left silent.

**[MINOR] `no-change` bucket and log line don't distinguish "flat" from "shrank"**
