=== WHY THESE EXIST (observed, do not re-derive) ===

The bridge's client sent three different tool tables in one morning -- 8,
then 12, then 18 tools -- because its extension discovery races the first
request. That cut the shared KV prefix from ~19,200 tokens to 1,674 (the
built-ins-only block). Three consecutive requests then prefilled ~19k tokens
at ~92 s each and all three were discarded when the client timed out, because
the prefix cache only checkpoints a boundary after the fork ledger has seen
two request lines diverge there -- so the first request of a new shape stores
nothing and the next one is no better off.

=== BEHAVIOUR 1: rescue capture (in generate_deltas) ===

Constants: DEFAULT_PREFIX_CACHE_RESCUE_MIN_TOKENS = 4096,
env override PREFIX_CACHE_RESCUE_MIN_TOKENS_ENV =
"MLX_SERVE_PREFIX_CACHE_RESCUE_MIN_TOKENS".

The guard, verbatim from the source, fires when ALL hold:
  - capture_pool is not None
  - `boundaries` is empty (no ledger boundary lay inside this prefill span)
  - len(prompt_to_prefill) >= the threshold
  - cache_prompt is non-empty
  - capture_pool._has_node_for(list(cache_prompt)) is False
Effect: snapshot_prefix_cache(prompt_cache) -> PrefixCacheNode(tokens=
cache_prompt, depth=capture_pool.token_depth(cache_prompt)) -> add_node,

  b) does not fire when a boundary WAS captured during the prefill (the

  c) does not fire below the threshold; and honours the env override in both

=== BEHAVIOUR 2: PrefixKVCachePool.token_depth ===

    def token_depth(self, tokens: list[int]) -> int

Counts <|im_end|> occurrences in `tokens`; returns 1 when the tokenizer has
no <|im_end|>. It exists because _boundary_depth looks a prefix up in the
fork ledger and returns 0 for one the ledger has never seen -- which every
rescue capture is. Test: correct count for 0/1/several boundaries; the
no-<|im_end|> tokenizer returns 1; and that it agrees with _boundary_depth
for a prefix the ledger DOES know (that agreement is the point of the split).

=== BEHAVIOUR 3: run_keepalive ===

    def run_keepalive(stop_event, interval, should_stop, emit, *, protocol)

Module-level, used by both the ollama and openai heartbeats. Loop: wait on
stop_event; return if should_stop(); else call emit(). On OSError from emit
it sets stop_event, logs INFO event "keepalive_client_gone" with protocol and
error (the exception CLASS NAME, e.g. "BrokenPipeError"), and returns.

Cover:
  a) emit raising BrokenPipeError -> returns without propagating, stop_event
     is set, exactly one keepalive_client_gone record, error field is
     "BrokenPipeError". ConnectionResetError likewise.
  b) it does NOT swallow a non-OSError: e.g. ValueError from emit propagates.
     This matters -- the point was to stop tracebacks from a gone client, not
     to make the thread silent about real bugs.
  c) normal operation: emits repeatedly until stop_event is set; returns
     promptly when should_stop() flips true, without another emit.
  d) both wiring sites still start a thread and still stop it -- assert via
     the existing streaming tests if one already covers the heartbeat
     (test_ollama_stream_emits_keepalive_when_token_source_stalls exists),
     otherwise leave (d) out and say so.

Use short intervals (a few ms) so nothing sleeps. No real sockets, no
threads left running at test exit.

=== TASK 1: stable-est-first datetime ===

The weekday is the fastest-changing field and it is FIRST, so at midnight the

=== TASK 2: freeze the tool table (the real one) ===

A request must never go out with a partially-discovered tool list. Either
one of these is acceptable; pick based on what the code actually supports and
say which you picked and why:

  (a) Block the first request until extension tool discovery has settled,
      then freeze the list for the process lifetime.
  (b) Resolve the full tool list once during boot, before the agent can
      accept work, and treat later registrations as an error or a warning
      rather than a silent mutation.

Starting points: `Agent::extend_tools` (src/agent.rs:1278) sets
`cached_tool_defs = None` on every call -- the code already expects the table
to change under it, and that expectation is what breaks the cache.
Registration sites: src/extension_tools.rs:719 and src/agent.rs:9416.
`ToolRegistry` (src/tools.rs:2646) is a Vec and is order-stable; the
built-in eight from `create_all_tools` (src/sdk.rs:123) are fixed. The
instability is entirely in when the extension wrappers arrive.

Requirements:
  - Two runs with the same config must produce a byte-identical tool array.
  - No request may observe a partial table. A boot that is slow is fine; a
    boot that is fast and wrong is not.
  - Do not silently drop a tool that arrives late. Dropping it changes what
    the agent can DO in exchange for a cache hit, which is a bad trade made
    invisibly. Log it, or fail, or block for it -- your choice, but it must
    be visible.
  - If discovery can genuinely never settle (no completion signal exists in
    the runtime), STOP and report that rather than inventing a timeout that
    silently truncates the tool list. A guessed timeout reintroduces exactly
    this bug on a slow machine.

Add a test that the assembled tool list is deterministic across two
independent builds with identical inputs. Prefer asserting the full ordered
name vector over asserting a count.
