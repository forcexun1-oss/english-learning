Today's session shifted from board deployment to **network proxy** debugging on macOS. You pasted a **Clash Meta** `config.yaml`, asked why traffic kept rising even when you thought the proxy was off, and wanted only **Claude Code** routed through the proxy while everything else stayed direct.

## Vocabulary

- **proxy / proxy traffic** – network requests forwarded through an intermediary (here, Clash on port `7890`).
- **rule mode** – Clash routes each domain by `rules:` (e.g. `GEOIP,CN,DIRECT`, `MATCH,DIRECT`).
- **fake-ip / enhanced-mode** – DNS handling that can make apps behave as if a proxy is active even when you expect a direct path.
- **bypass** – hosts that should skip the proxy (your config lists `127.0.0.1` and `localhost`).
- **ESTABLISHED** – an active TCP connection; `lsof -i :7890` showed **Cursor** and **ChatGPT** already talking to localhost:7890.

## Grammar for Agent Instructions

| Rough | Better |
|-------|--------|
| *is qize enable?* | Is **QUIC** enabled? |
| *claode code 走代理* | Only **Claude Code** should use the proxy. |
| *又打不开了* | **It won't open again** / **The site won't load again.** |
| *执行了proxy_off 也还是有代理* | I ran `proxy_off`, but **traffic still goes through the proxy.** |

When debugging proxies with a coding agent, **paste the config file** and state the symptom clearly: unexpected bandwidth, sites failing after a toggle, or apps still hitting `:7890`. Ask a **narrow routing question**: *"If I only need Claude Code to use the proxy, what rules should I add?"* Pair Chinese questions with one English sentence so the agent can quote your exact goal. Use commands as evidence—`lsof -i :7890` proves which processes hold connections, which matters more than whether the menu bar says "proxy off."
