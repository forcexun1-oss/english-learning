# English Learning — 2026-06-17

Today's session moved from **reviewing Codex's edge-agent implementation** to **deploying Qwen3-TTS on Rockchip boards** and tightening deployment docs.

## Vocabulary

- **e2e (end-to-end)** – a full pipeline test from input to output; you asked to *verify the Z1a e2e state*.
- **worktree** – Git's view of your working files; GitNexus flagged the branch as *broad/high-risk* because many dirty files sat outside your module slices.
- **caveat** – an important limitation; you listed linker and PyO3 issues as *caveats* before merging.
- **stale deploy scripts** – scripts that no longer match the current architecture (e.g. after consolidating to a single port).
- **RKNN / NPU** – Rockchip's runtime for models on the neural processing unit; conversion targets the NPU, not plain CPU inference.
- **VRAM** – video/GPU memory on the SoC; relevant when choosing whether TTS runs on the RK1828 or RK3576.

## Grammar for Agent Instructions

| Rough | Better |
|-------|--------|
| *So tts should deployed on the 3576* | **TTS should be deployed on the RK3576.** |
| *let test* | **Let's test it.** |
| *after convertion* | **after conversion** |
| *Firstly we should convert them to RKNN2* | **First, we should convert them to RKNN.** |
| *hold off for now, just keep TTS on the 1828* | Clear and natural — good directive when scope shifts. |

When asking about hardware, name the board explicitly: *Is it running on the RK1828?* beats a bare *1828* if the agent might confuse model numbers.

For hook debugging, precise product terms help: *The English Coach hook is registered, but there is no terminal output* signals you expect `systemMessage` visibility, not just silent context injection.
