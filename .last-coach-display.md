## Findings (written into ui.md)
- **USS:** there is no `line-height` and no `box-shadow`. `filter` exists but has no drop-shadow, so shadows stay as a separate element. `:last-child` and `:first-child` are not supported.
- **Font:** the spec's USS `-unity-font` route draws Chinese characters blank once we use our own text settings (which the line-breaking rules need). `UiRoot` now builds the NotoSansSC font asset in code instead. Side effect: "·" renders full-width.
- **Line breaking:** Unity's naming is the reverse of what you would guess. "leading" means opening brackets (may not end a line); "following" means closing punctuation (may not start a line). The rules have no public setter, so `UiAssetBuilder` generates the asset.
- **Key order:**
  - UI Toolkit reads input early in each frame, before every key driver's Update. I confirmed this from the engine's frame-loop order and a runtime check, not from real key presses.
  - So a driver calling `Input.ResetInputAxes()` cannot hide that frame's key from UI Toolkit.
  - Any driver must also swallow input on the frame its screen closes. Otherwise the same Esc opens the pause menu. `GalleryDriver` does this.
- **Draw order:** IMGUI draws on top of UI Toolkit. In one windowed run where I pressed no keys, the Hub labels, buttons and the IMGUI pause menu all appeared above the open gallery.
  - **Decision for U1:** while a UI Toolkit screen is open, the overlapping IMGUI layers need to be hidden, or the old Hub HUD will draw over the new talent screen.
  - I suggest `GameApp.OnGUI` skips the HUD and layers below the pause menu (Order &lt; 900) whenever a UI Toolkit screen is open.
  - U0 leaves IMGUI drawing unchanged.
- **Click mapping:** the coordinate conversion used to decide whether a click lands on UI hit the right button in testing.
