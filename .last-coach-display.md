### Issues (ranked)

**[CRITICAL] The model never produces text: thinking fills the token budget**
File: `Assets/Scripts/Game/Agents/PiHost.cs:43, 58`, with the effect at `PiRpcChannel.cs:73, 86`
Confidence: HIGH (verified in the transcript)
- **Scenario:** every call after the first ends `stopReason=length` with only thinking. `text.Length == 0`, so `result = null` and the rule-based fallback always wins. "Empty text" is therefore the normal outcome, not just a symptom of the timeouts.
- **Fix:** turn thinking off on the Ollama side. Options:
  - Use an Ollama model or Modelfile that doesn't think.
  - Have pi send `reasoning_effort: "none"`. Ollama's `/v1` endpoint maps that to `think:false`; this needs a pi provider/compat option, so check `packages/ai` openai-completions.
  - Use the native `/api/chat` with `think:false`.
  - As a stopgap: lower `maxTokens` (around 256) so calls finish fast, and add `/no_think` to the system prompt if the model honours it.
- Also log `stopReason` and the thinking length when `agent_end` arrives with empty text, so this failure is visible and not silently swallowed.

**[HIGH] Ollama overload: two pi channels plus KevScorer on one model**
File: `GameApp.cs:25-35`, `AgentCoordinator.cs:41, 53`
Confidence: HIGH that they compete (Curl 28 in botD, nemesis timing out while companion is generating); MEDIUM that this alone pushes calls past 45s.
- **Scenario:** at the end of a run, nemesis Refine and companion Say start together, and KevScorer keeps firing during play. With about 2,000 tokens per pi call, the second request in the queue easily waits more than 45s.
- **Fix:** fixing the CRITICAL issue removes most of this. In addition, run the agent calls one at a time through a single shared gate (one Ollama request in flight), or skip Kev requests while a pi call is running.

**[MEDIUM] The 45s timeout counts time spent waiting for the gate, and runs back-to-back on one channel**
File: `PiRpcChannel.cs:56, 77`, `AgentCoordinator.cs:27, 53`
Confidence: HIGH (verified by reading)
- **Scenario:** the timeout clock itself starts after the gate. But Greet for the next run waits behind the previous reflect on the same companion channel, and each can take up to 45s. A slow call therefore delays the next one by up to 45s, and by then the run may be over (batch quit, or a stale greeting).
- **Fix:** drop or cancel a stale Ask instead of queuing it (for example, if `busy`, return null right away for Greet), or pass a deadline in from the caller.

**[MEDIUM] A persistent companion session plus a reasoning model makes prompts grow**
File: `PiHost.cs:62`, `GameApp.cs:26`
Confidence: MEDIUM
- **Scenario:** every run appends turns to the `companion` session. Thinking-only turns are removed by `context_edit`, but successful ones (with their thinking) stay. As prompt evaluation grows, calls slow down; the transcript shows `input` rising to 982 tokens.
- **Fix:** keep it stateless (`--no-session`, like nemesis), because memory already lives in the save file and goes into the prompt. Or cap and compact the session.

**[LOW] The first `agent_end` ends the wait, even if pi retries**
File: `PiRpcChannel.cs:74`
Confidence: MEDIUM (`agent-session.ts:1144` emits `agent_end` with `willRetry`)
- **Scenario:** on a provider error that pi retries, the first `agent_end` has `willRetry: true`. Ask stops there with empty text, and the retry's output lands in the queue, where the next Ask's drain discards it.
- **Fix:** add `public bool willRetry;` to `Ev` and treat `agent_end` as final only when `!willRetry`.

**[LOW] A pi error response to the prompt is ignored, so the call waits the full 45s**

- **Fix:** add `success` and `error` fields to `Ev`. On `type=="response" &amp;&amp; !success`, log the error and end right away.

**[LOW] Stale output from a killed process can leak into the next Ask**
File: `PiRpcChannel.cs:35, 63, 97-98`
Confidence: LOW (speculative)

- **Fix:** give each process its own queue (create a new `ConcurrentQueue` in `EnsureStarted` and capture it in the lambda), or filter on a generation counter.

**[LOW] Killed or exited `Process` objects are never disposed**

Confidence: HIGH

- **Fix:** call `proc.Dispose()` after `Kill()`, and also when `HasExited` is detected in `EnsureStarted`.

### Checked and ruled out (verified)
- **Stdin side:** `ArgumentList` quoting of the system prompt, and `StandardInputEncoding = new UTF8Encoding(false)` (no BOM). pi's own JSONL reader splits on `\n`, and Mono `WriteLine` on macOS writes `\n`.
- **Output side:** `Flush` after each write, and `Encoding.UTF8` on stdout.
- **Paths:** the space in the working-directory path, and the PATH that resolves `node`.
- **Parsing:** `JsonUtility` on event shapes it doesn't model: unknown fields are ignored, and non-JSON lines are caught and become `null`.
- **Coroutine structure:** `yield` inside `try/finally` is allowed in iterators; `busy` is always reset; the `break` at line 74 only leaves stale lines, which the next drain discards.
- **Draining at the start of Ask:** it runs before `Send`, so it can't drop a reply to the current prompt.
- **`HasExited`:** behaves as expected.
- **Process start:** a failure to start or an early exit would show as "process exited" or "start failed", and neither appears in the logs.
