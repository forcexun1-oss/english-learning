**[CRITICAL] H2 proptest `vad_cut_invariant_matches_contract` is a textbook circular oracle**
File: `rust/apps/edge-agent/src/runtime_bridge.rs:731-757`

The test's `should_cut` predicate (lines 735-737) is a line-for-line reimplementation of the production cut condition at lines 412-415:

```
// Test oracle (line 735-737):
speech_ms &gt;= endpoint.min_speech_ms
    &amp;&amp; (silence_ms &gt;= endpoint.trailing_silence_ms
        || speech_ms + silence_ms &gt;= endpoint.max_segment_ms)

// Production code (line 412-415):
speech_ms &gt;= endpoint.min_speech_ms
    &amp;&amp; (silence_ms &gt;= endpoint.trailing_silence_ms
        || speech_ms + silence_ms &gt;= endpoint.max_segment_ms)
```

This is exactly the pattern the handoff doc section 1 warns against: "AI 写的代码 + AI 写的测试若共享同一假设,会把「错但自洽」的行为固化成'通过'". If the cut formula has a bug (e.g., should be `&gt;` not `&gt;=`; should use cumulative not resettable `silence_ms`), neither the code nor the test would catch it. Additionally, the `!should_cut` branch (line 751-753) only asserts `segment.is_some()` after closing the channel -- it does NOT assert the segment was NOT already cut before channel closure, so it cannot distinguish "correctly deferred cut" from "prematurely cut then returned leftover". The test has zero oracle value for finding real bugs.

Furthermore, `frame_ms` computes data length as `samples * 2`, and `audio_frame_duration_ms` computes `(data.len() / 2 * 1000) / sample_rate`. For durations that don't produce exact integer samples (e.g., 30ms at 16kHz = 480 samples = exact, but other values may truncate), the test oracle computes total ms by summing the requested durations, not the actual durations after integer truncation. This discrepancy is masked by the fact that the range `30..300` at 16kHz happens to always produce clean multiples, but it's another signal that the oracle was derived from the specification text rather than independently modeling the actual frame behavior.

Fix: Replace the re-derived oracle with a **state-machine oracle** or **known-answer table**. For proptest, the invariant should be something the implementation could violate while the oracle could not -- e.g., "a returned segment always contains &gt;= min_speech_ms of speech data", "silence frames are never included in pcm", "no segment exceeds max_segment_ms + one frame". These are one-sided invariants derivable from the spec without reimplementing the full cut logic.

**[HIGH] `vad_endpoint_discards_sub_minimum_speech_interrupted_by_silence` -- misleading name and assertion locks implementation artifact**
File: `rust/apps/edge-agent/src/runtime_bridge.rs:650-664`

The test name says "discards" but it asserts the segment IS returned (`unwrap().unwrap()`) with `pcm.len() == 6_400`. What actually happens: 200ms speech (&lt; min_speech 240ms) + 800ms silence does not trigger the cut condition, but when the channel closes (drop tx), the fallback at line 424 returns `Some(SpeechSegment)` if any speech was seen. So this test actually verifies "sub-minimum speech is still returned as a segment on channel close" -- the opposite of what "discards" implies.

The contract (B7 handoff section 4.3) says speech &lt; min_speech_ms should not be CUT by silence, not that it should be discarded entirely on stream end. The test name is wrong and the assertion (`pcm.len() == 6_400`) locks a specific byte count that comes from `16000 * 200 / 1000 * 2 = 6400` -- an implementation detail of frame sizing, not a contract boundary.

Fix: Rename to `vad_endpoint_does_not_cut_sub_minimum_speech_on_silence` and assert the behavioral invariant (cut condition not triggered while frames remain, segment eventually returned on close) rather than exact byte count.

**[HIGH] C1 filler cancellation test uses timing-based synchronization (flaky)**
File: `rust/apps/edge-agent/src/agent_core/reasoning.rs:659-696`

The `run_turn_cancellation_during_filler_send_stops_without_actions` test uses `tokio::time::sleep(Duration::from_millis(50))` (line 687) to wait for the filler send to be in-flight, then cancels. Unlike the other two C1 tests which use `Notify` for deterministic synchronization, this one hopes 50ms is enough for the task to reach the filler send point. On a loaded CI machine this can race: either cancellation fires before the task reaches the filler path (testing early cancellation instead), or the filler send completes before cancellation arrives. The bounded(0) channel helps create backpressure, but the 50ms sleep is still non-deterministic.

The other two C1 tests (chat_stream cancellation at line 586 and tool execution at line 619) correctly use `Notify` barriers -- this one should do the same.

Fix: Add a `Notify` signal to the test LLM or executor that fires when the filler send is attempted (or just before), so the test can synchronize deterministically rather than relying on timing.
