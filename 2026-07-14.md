# Manual/Custom KV-Cache Trim for Prefix Reuse — Feasibility &amp; Plan

Date: 2026-07-14
Model: `qwen3.6-35b-mlx-q6-aligned` (`model_type: qwen3_5_moe`), expert-streaming, optional MTP sidecar
Interpreter: `/Users/youxun/project/mlx/.venv_build/bin/python` → resolves `mlx_lm` to the in-tree checkout at `/Users/youxun/project/mlx-lm/mlx_lm` (confirmed: `mlx_lm.models.cache.__file__` == `/Users/youxun/project/mlx-lm/mlx_lm/models/cache.py`).

## Verdict

**Manual array-slicing trim: NOT FEASIBLE (dead end).**
**Prefix KV reuse across the diverging timestamp: FEASIBLE-WITH-CAVEATS — via checkpoint/snapshot, not trim.**

`can_trim_prompt_cache()` returns `False` for a correct, structural reason, not an implementation gap: this is a **hybrid attention model** whose cache is 30 recurrent `ArraysCache` (Gated-DeltaNet linear-attention state) + 10 `KVCache`. A recurrent state is a fold over all history and is mathematically not sliceable back to an earlier token — so trimming (manual or upstream) can never work for those 30 layers. The correct primitive is **checkpoint/restore** (which `ArraysCache` already implements and which the MTP prompt-state path already uses on this exact cache). The geometry is favorable (the divergent timestamp sits at the very end of an ~8500-token static block), so a checkpoint at the static-prefix boundary recovers essentially the entire prefill.

Strongly consider the **client-side alternative first** (round/relocate the timestamp in `pi_agent_rust`): it makes the *already-shipped* pure-growth reuse fire with **zero server-side risk**. Details in the last section.

## Root cause (evidence)

### 1. The cache is hybrid; 30 of 40 layers are structurally non-trimmable

`make_prompt_cache(model)` defers to the model's `make_cache` (`cache.py:31-32`). For this model the chain is `qwen3_5_moe.Model → Qwen3_5Model.make_cache → language_model.make_cache` (`qwen3_5.py:567-568`), which returns:

```python
# mlx_lm/models/qwen3_5.py:345-346
def make_cache(self):
    return [ArraysCache(size=2) if l.is_linear else KVCache() for l in self.layers]
```

`is_linear = (layer_idx + 1) % full_attention_interval != 0` (`qwen3_5.py:213`). With `num_hidden_layers=40`, `full_attention_interval=4` (from `config.json`), layers 3,7,…,39 (10 layers) are full-attention `KVCache`; the other **30 are `ArraysCache`** holding Gated-DeltaNet recurrent state.

`can_trim_prompt_cache` is `all(c.is_trimmable() ...)` (`cache.py:88-92`). `KVCache.is_trimmable()==True` (`cache.py:385`), but `ArraysCache` **does not override `is_trimmable`**, so it inherits `_BaseCache.is_trimmable()==False` (`cache.py:153-154`). One non-trimmable layer ⇒ the whole `all(...)` is `False`. That is exactly what the live debug logging observed.

This is not model-specific bad luck or MTP wiring:
- **Not MTP.** `load_model_once` builds `mtp_model` as a *separate* `Qwen35MoeMTP` module (`serve_ollama_stream.py:493-497`; `mlx_lm/mtp.py:140-167`) with its own `make_cache` returning `[KVCache()]` (`mtp.py:59-60`). It does **not** wrap or replace the primary model's cache. The primary cache is non-trimmable whether or not the sidecar is loaded.
- **Not expert-streaming.** The MoE/mmap path affects weight residency, not cache class.
- **Structural.** Gated-DeltaNet stores a fixed-size running state independent of sequence length: `cache[1]` is the recurrent state `[B, Hv=32, Dv=128, Dk=128]` and `cache[0]` a tiny conv window (`qwen3_5.py:149-199`; kernel from `gated_delta.py:151-163`: `state = state*decay + k*delta; y = state*q`). The state at token *n* is overwritten as tokens *n+1…* fold in; it cannot be reconstructed. `ArraysCache` therefore offers `can_checkpoint()==True`/`checkpoint()`/`restore()` (`cache.py:634-647`) **instead of** trim.

The in-tree spec-decode plan already documents this exact conclusion for the sibling `qwen3_next` cache ("30× ArraysCache … `is_trimmable()==False` … A recurrent state cannot be 'trimmed' … but it CAN be checkpointed and restored") — `docs/plans/2026-07-11-spec-decode-checkpoint-rollback.md`.

### 2. Why the current prefix pool never reuses anything for this client

`prepare_prefix_kv_cache` has two reuse paths (`serve_ollama_stream.py:766-790`):
- **Pure-growth** (`prefix_len == len(cached_tokens)`): no trim needed — this is the fix shipped today (`serve_ollama_stream.py:768-772`, mirrored by the `needs_trim` guard in `_longest_prefix_slot`, `serve_ollama_stream.py:184-189`).
- **Divergent** (`prefix_len &lt; len(cached_tokens)`): gated on `can_trim_prompt_cache(state.cache)` (`:773`) → always `False` here → falls through to full rebuild (`:786-790`).

The client makes **every** request divergent: `pi_agent_rust` appends a live timestamp at the end of the system prompt — `let _ = write!(prompt, "\nCurrent date and time: {date_time}")` (`/Users/youxun/project/pi_agent_rust/src/app.rs:185`, rendered by `format_current_datetime()` → seconds-resolution `Local::now()`, `app.rs:357-366`). Two requests issued seconds apart share every token up to that line, then diverge. So the reusable prefix is real and large, but reaching it requires trimming the diverging tail — the one thing this cache cannot do.

### 3. Geometry: the shared prefix really is ~8500 tokens (this is what makes any fix worthwhile)

The chat template (`/Users/youxun/models/qwen3.6-35b-mlx-q6-aligned/chat_template.jinja`) renders the system block as:

```
&lt;|im_start|&gt;system
# Tools ... &lt;tools&gt;{tool json}...{tool json}&lt;/tools&gt;
[fixed multi-hundred-token tool-call format instructions]
{system message content}      ← pi's system text, whose LAST line is "Current date and time: X"
&lt;|im_end|&gt;
```

i.e. **the entire tool-schema block (~8500 tok) precedes the system content, and the volatile timestamp is the trailing line of that content.** Since `longest_common_prefix` counts from token 0 (`serve_ollama_stream.py:750-755`), the first divergence is at the timestamp, giving LCP ≈ 8500+ of ~8600 — matching the empirical "8500/8600 identical, small tail differs." Everything *before* the timestamp (tool JSON, format instructions, static guidelines, per-cwd project context) is byte-stable within a session. A checkpoint taken at that boundary is reusable by essentially every subsequent request in the session.

Expected payoff: cold turn stays ~70 s; establish once; thereafter each turn prefills only the ~100-token tail instead of ~8600 → same order-of-magnitude win the pure-growth fix already delivers, but for the divergent-tail case that dominates this client.

## Feasibility analysis

### Manual array-slicing trim — dead end

For the 10 `KVCache` layers a manual trim is trivial and safe (decrement `offset`; keys/values are per-token, `cache.py:388-391`). For the 30 `ArraysCache` layers it is **impossible without silent corruption**: there is no per-token axis to slice — `cache[1]` shape does not depend on sequence length. Any "manual trim" would leave the recurrent state as the fold over the *old* tail while the new tail is appended on top, producing plausible-but-wrong logits with no error. Given the task's own warning ("a wrong-but-not-crashing trim would be worse than no trim"), this rules out manual trimming outright. Upstream `mlx_lm` has not and structurally will not add trim for recurrent caches — `LRUPromptCache.fetch_nearest_cache` itself only uses the trim path when `can_trim_prompt_cache` is true and otherwise falls back to exact/shorter deepcopy matches (`cache.py:1712-1732`).

### Checkpoint/snapshot-based prefix reuse — the viable path (already proven on this cache)

The mechanism we need already exists and is validated on this exact mixed cache by the MTP prompt-state store: it snapshots `(KVCache | ArraysCache)` lists via `copy.deepcopy` at a token boundary, validates an exact fingerprint, then restores and continues generation (`mlx_lm/generate.py:715-846`, esp. `_mtp_cache_fingerprints` at `:715-735` which explicitly branches `KVCache.meta_state` vs `ArraysCache.checkpoint()`, and `_mtp_clone_prompt_state = copy.deepcopy` at `:742-743`). `ArraysCache` deepcopy/checkpoint is cheap because entries are immutable MLX arrays replaced each forward (`cache.py:628-647`; snapshot ≈ reference/array copy, not recompute).

**Numerical soundness:** restoring the cache at boundary *P* and prefilling `tokens[P:]` yields logits bit-identical (modulo the normal run-to-run nondeterminism) to a full prefill, because the state at *P* *is* what a full prefill produces at *P*, and the tail attends only to the identical `[:P]` region. This is the same invariant the MTP prompt-state correctness benchmark relies on (`docs/plans/2026-07-12-mtp-correctness-benchmark-and-optimization.md`).

**The one caveat vs. MTP:** MTP keys on *exact full-prompt* match; we need *prefix* match (snapshot at *P*, reuse when `tokens[:P]` match, then prefill the tail). Mechanically identical snapshot/restore; different key + a subsequent tail prefill.

## Implementation plan (function-level, `serve_ollama_stream.py` only)

Design: give each pool slot an immutable **prefix snapshot** (deepcopied mixed cache at boundary *P* + the exact `P` prefix tokens). Per request that matches the prefix, deepcopy the snapshot into a fresh working cache and prefill only the tail. All under the existing `generation_lock`.

### Step 1 — Snapshot primitive (new module-level helpers)

Add near `prepare_prefix_kv_cache`:

- `snapshot_prefix_cache(cache) -&gt; list` — `copy.deepcopy(cache)` (reuse the MTP-validated pattern; do **not** invent per-class logic). Call `mx.eval` on `[c.state for c in cache if not c.empty()]` first, mirroring `_mtp_make_prompt_state_bundle` (`generate.py:820-825`), so the deepcopy captures materialized arrays.
- `restore_prefix_cache(snapshot) -&gt; list` — `copy.deepcopy(snapshot)` (snapshot stays pristine for the next request; same discipline as `LRUPromptCache.fetch_nearest_cache`, `cache.py:1716`).
- `prefix_cache_nbytes(cache) -&gt; int` — `sum(c.nbytes for c in cache)` (`nbytes` exists on both classes: `cache.py:414-417`, `751-753`) for slot accounting.

### Step 2 — Extend `PrefixKVCacheState` (`serve_ollama_stream.py:104-116`)

Add fields: `prefix_snapshot: object | None = None`, `prefix_tokens: list[int] | None = None`, `prefix_len_snapshot: int = 0`, `prefix_snapshot_nbytes: int = 0`. Clear them wherever `cache`/`tokens` are reset (esp. `_new_or_evict_slot`, `serve_ollama_stream.py:163-167`, and the failure path `generate_deltas` `:740-742`).

### Step 3 — Selection: allow checkpoint-reusable slots (`_longest_prefix_slot`, `serve_ollama_stream.py:170-192`)

Today a divergent slot is only eligible if `can_trim_prompt_cache(slot.cache)`. Add an OR branch: a slot is also eligible when it carries a `prefix_snapshot` whose `prefix_tokens` is a byte-exact prefix of the incoming prompt and `prefix_len_snapshot &gt;= min_prefix_tokens`. Keep `_is_meaningful_prefix` gating (`:194-204`). Do **not** relax the exact-token check — an approximate match would poison generation.

### Step 4 — Reuse + establish in `prepare_prefix_kv_cache` (`serve_ollama_stream.py:758-790`)

Insert a checkpoint branch **before** the existing `can_trim_prompt_cache` branch (`:773`):

1. **Reuse:** if `state.prefix_snapshot` exists and `state.prefix_tokens == prompt[:P]` (P = `prefix_len_snapshot`) and `P &lt; len(prompt)`:
   `state.cache = restore_prefix_cache(state.prefix_snapshot)`; set `state.tokens = list(prompt[:P])`, bookkeeping (`last_prefix_len=P`, `last_tokens_prefilled=len(prompt)-P`); `return state.cache, prompt[P:]`. (Fast path.)
2. **Establish (no snapshot yet, but a long divergent common prefix exists):** compute `P = longest_common_prefix(prompt, cached_tokens)`. If `P &gt;= min_prefix_tokens` and `P &lt; len(cached_tokens)` (divergent) and `can_trim_prompt_cache` is `False`: build the boundary cache without a second full prefill by **splitting this request's own prefill** — return a fresh `make_prompt_cache(model)` plus a marker so `generate_deltas` prefills `prompt[:P]`, snapshots there, then prefills `prompt[P:]`. (See Step 5. This request costs the same ~70 s it costs today, but now yields the snapshot.)
3. Else fall through to the unchanged trim/rebuild logic.

Rationale for establishment-by-split: Req 1 (cold) can't know *P*; Req 2 reveals *P* via LCP with Req 1 and, because it must prefill anyway, snapshots mid-prefill at no extra latency. Req 3+ hit the fast path.

### Step 5 — Snapshot-on-prefill hook in `generate_deltas` (`serve_ollama_stream.py:639-658`)

When `prepare_prefix_kv_cache` signals "establish at P", change the single prefill loop (`:644-651`) into two segments: prefill `prompt[:P]` (`generate_step(..., max_tokens=0)`), then `state.prefix_snapshot = snapshot_prefix_cache(prompt_cache)`, `state.prefix_tokens = list(prompt[:P])`, `state.prefix_len_snapshot = P`, `state.prefix_snapshot_nbytes = prefix_cache_nbytes(prompt_cache)`; then continue prefilling `prompt[P:]`. Everything downstream (generation, `cache_state.tokens = cache_prompt` at `:652`) is unchanged.

### Step 6 — Bound snapshot memory (eviction, `_new_or_evict_slot` `:156-168`)

Snapshot ≈ **~200 MB** for this model at P≈8600 (10 KV layers × keys+values `[1,2,P,256]` ≈ 176 MB; 30 linear layers × recurrent `[1,32,128,128]` ≈ 31 MB; measure precisely via `mx.get_active_memory` delta or the existing `MTP_PROMPT_STATE_MEASURED_BYTES` table, `serve_ollama_stream.py:321-322`). With `kv_slots` slots this is `kv_slots × ~200 MB`. Drop `prefix_snapshot` on eviction; optionally add a `--kv-snapshot-budget-bytes` cap that refuses to establish a new snapshot when over budget (mirror the `logical_budget` guard in `MTPPromptStateSessionManager.generation`, `:373-378`).

## MTP prompt-state interaction (no new trimming needed)

Prefix reuse and MTP speculative decode are **already mutually exclusive**: MTP decode is eligible only when `prompt_cache is None` (`serve_ollama_stream.py:666-673`; the `prefix_cache_conflict` fallback at `:682-683`). Any request that reuses a prefix cache has `prompt_cache is not None`, so it runs plain `stream_generate` and never touches `MTPPromptStateStore`. Therefore:
- **No** need to trim/invalidate MTP-side prompt state when reusing our snapshot — the paths don't co-occur.
- `MTPPromptStateStore`/`MTPPromptStateSessionManager` (`serve_ollama_stream.py:214-429`) remain untouched; they self-manage via exact-key LRU (`generate.py:775-804`).
- Keep the two stores clearly separate in code and naming; our snapshot is a raw cache list, not an `MTPPromptStateBundle`.

Keep an integration-style equivalence check (optional, gated on the real interpreter/model, not CI): full-prefill logits vs. snapshot-restore+tail logits for the same prompt must match first-token — the STEP18 correctness gate style (`MLX_STEP18_PREFIX_KV_CACHE_SPEC.md:47-52`).

## Risks &amp; edge cases

- **Silent poisoning (highest):** reuse without exact `tokens[:P]` match. Mitigation: byte-exact token compare before restore (Step 3/Test 5); never approximate.
- **Partial establish failure mid-request:** if generation after snapshot raises, the existing `except BaseException` clears `state.cache`/`tokens` (`:739-743`); extend it to also clear the snapshot fields so a corrupt half-snapshot is never reused.
- **Thread-safety:** all snapshot/restore/deepcopy happen under `generation_lock` (`serve_ollama_stream.py:1528`, `:1643`); single-generation serialization is preserved. Do not snapshot off-lock.
- **Memory/perf cost of the copy:** ~200 MB deepcopy per reuse and per snapshot. That is negligible vs. an 8500-token MoE prefill (tens of ms vs. ~70 s), but multiplied by `kv_slots` for storage — bound it (Step 6). Watch `vm_stat` compressor as the plans warn (`docs/plans/2026-07-11-spec-decode-checkpoint-rollback.md`).
- **Boundary drift:** if per-cwd project context or tool ordering changes mid-session, *P* shifts; the exact-prefix check simply misses and re-establishes — correct, just a one-turn cost.
- **`mx.eval` before deepcopy:** required so lazily-computed cache arrays are materialized (mirror `generate.py:820-825`); omitting it risks copying unevaluated graphs.
- **Eviction/LRU interplay:** snapshot lives on the slot; `_new_or_evict_slot` and session reuse must reset it consistently (Test 7).

## Simpler, lower-risk alternative (recommended sanity check — client side, out of scope to implement here)

The entire problem is self-inflicted by baking a **seconds-resolution** timestamp into the cached region (`pi_agent_rust/src/app.rs:185`, `:357-366`). Two low-risk client changes eliminate it without touching the server:

1. **Coarsen the timestamp** (date-only, or hour) so consecutive requests within the window render byte-identical system blocks. The **already-shipped** pure-growth / exact-prefix reuse then fires with **zero** new server code or snapshot memory.
2. **Relocate the volatile line** out of the cached prefix — e.g. inject "Current date and time" as a separate trailing ephemeral message appended after history rather than inside the system prompt. (Less clean than (1) because each turn still ends divergent, but it stops capping the *system-block* prefix.)

Option (1) is by far the cheapest, lowest-risk fix and should be evaluated before committing to the server-side checkpoint work. The server-side plan above is the right choice only if the timestamp must stay at seconds resolution inside the system prompt for product reasons, or if other clients also diverge mid-prompt.
