## Blocking Issues

### BLOCKING-1: B4 `ExecutionGuard::check` is not `async` but B2's ReAct loop is fully async

**Module:** B4 Guard (workpackages.md line 346)

```rust
pub trait ExecutionGuard: Send + Sync {
    fn check(&amp;self, action: &amp;Action, ctx: &amp;GuardContext) -&gt; GuardVerdict;
}
```

This is the only non-async trait method on the hot path. Every other module in B-group is async. The design doc at SSOT section 4.4 states Guard decisions must be "pure memory, minimal overhead" -- and that is true today. But the `GuardContext` already contains `StateSnapshot` (from B5), and the stated evolution rules say "policy types expand via policy.toml." Once policies involve frequency-rate checks (which require consulting the AuditLog or a counter store), or state queries that go through an async `StateStore`, `check` being sync becomes a breaking change.

**Fix:** Make it `async fn check(...)` now. If the first implementation is purely in-memory, the async overhead is negligible (a trivial poll). This follows the same reasoning that made B1 MemoryStore async "because SQLite needs spawn_blocking" -- plan for the known variation point. The alternative is to accept the sync signature and accept a future breaking change, but that contradicts the stated "only-add" evolution rule.

### BLOCKING-2: A4 `Llm::chat_stream` return type is `Result&lt;()&gt;` -- there is no way to return `Usage` from the stream path

**Module:** A4 Llm (workpackages.md lines 161-166)

```rust
async fn chat(&amp;self, messages: &amp;[Message], tools: &amp;[ToolDef]) -&gt; Result&lt;LlmResponse&gt;;
// LlmResponse has: content, tool_calls, usage

async fn chat_stream(&amp;self, messages: &amp;[Message], tools: &amp;[ToolDef], tx: flume::Sender&lt;Chunk&gt;) -&gt; Result&lt;()&gt;;
// Chunk = TextDelta | ToolCall -- no Usage
```

The `Usage` struct (line 151) includes `first_token_ms` and token counts, which are essential for B8 observability (NFR: "full chain tracing + metrics"). The non-stream path returns `Usage` inside `LlmResponse`. The stream path returns `Result&lt;()&gt;` and `Chunk` has no `Usage` variant. The existing llm-gateway code at line 1329 already has a `TODO: stream path does not report token usage; counts remain zero`. This is a known gap being baked into the frozen contract.

**Fix:** Either (a) change `chat_stream` return to `Result&lt;Usage&gt;` (the function already awaits completion before returning -- the existing llm-gateway code shows this pattern at lines 1107-1111), or (b) add a `Chunk::Done(Usage)` variant. Option (a) is simpler and consistent with "the function completes when the stream is done." Specifically:

```rust
async fn chat_stream(&amp;self, messages: &amp;[Message], tools: &amp;[ToolDef], tx: flume::Sender&lt;Chunk&gt;) -&gt; Result&lt;Usage&gt;;
```

### BLOCKING-3: `ContextBuilder::build()` takes `system_prompt: &amp;str` and `current_input: &amp;str` as bare strings -- losing image from `AgentContext`

**Module:** B2 Reasoning (workpackages.md line 276)


`AgentContext` has `image: Option&lt;ImageRef&gt;` (the Y1-slimmed context), but `ContextBuilder::build` only receives `current_input: &amp;str`. ## Non-Blocking Improvements (ranked by impact)

### NB-1: `PromptStore::get` returns `Result&lt;&amp;str&gt;` -- interior borrow across async boundary

**Module:** B9 Prompt (workpackages.md line 462)

`PromptStore::get(&amp;self, key: &amp;str) -&gt; Result&lt;&amp;str&gt;` returns a borrowed `&amp;str` tied to `&amp;self`. If `PromptStore` is held behind `Arc` (which it will be in B2/B7), callers holding `&amp;str` across `.await` points will fight the borrow checker. `reload(&amp;self)` (line 464) implies interior mutability (the data can change), which makes returning `&amp;str` unsound without an `RwLock` guard.

**Recommendation:** Return `Result&lt;String&gt;` (owned clone), or `Result&lt;Arc&lt;str&gt;&gt;`. The cloning cost is negligible for prompt text accessed once per turn. This also makes `reload` safe without exposing lock guards in the public API.

### NB-2: `SkillEngine::list` returns `&amp;[Skill]` -- same borrow issue as NB-1

**Module:** B6 Skill (workpackages.md line 406)

`pub fn list(&amp;self) -&gt; &amp;[Skill]` has the same problem: borrowed return from a type that supports hot-reload (`load_from_dir`). Return `Vec&lt;Skill&gt;` or `Arc&lt;[Skill]&gt;` instead.

### NB-3: `B1 MemoryStore` lacks a `tail`/`recent_events` convenience method

**Module:** B1 Memory (workpackages.md line 232)

B2 `ContextBuilder` needs "the last N turns" to build context. The only query primitive is `get_events(session_id, offset, limit)`. To get the last N events, the caller must first call `event_count()` then `get_events(count - N, N)` -- two round-trips through an async trait (two `spawn_blocking` calls). This is the N+1 pattern.

**Recommendation:** Add `async fn recent_events(&amp;self, session_id: &amp;str, limit: usize) -&gt; Result&lt;Vec&lt;SessionEvent&gt;&gt;` which returns the last `limit` events (SQL: `ORDER BY rowid DESC LIMIT ? ... then reverse`). This is the primary query pattern for B2 and should be a first-class method.

### NB-4: `StateSnapshot` has `gear: Option&lt;String&gt;` -- stringly-typed

**Module:** B5 Trigger (workpackages.md line 367)

```rust
pub struct StateSnapshot { ..., pub gear: Option&lt;String&gt;, ... }
```

Gear is a finite set (P/R/N/D/S/L). Using `String` here is inconsistent with the design principle of "typed setters" (the `set_speed(kmh: f32)` right next to it). This is a minor fit-and-finish issue, but a `Gear` enum would be consistent and catch invalid values at compile time.

**Recommendation:** `pub gear: Option&lt;Gear&gt;` where `enum Gear { Park, Reverse, Neutral, Drive, Sport, Low }`.

### NB-5: `ImageRef` carries base64 data as `String` -- wasteful for in-process VLM path

**Module:** A4 Llm (workpackages.md line 130)

```rust
pub struct ImageRef { pub data: String, pub media_type: String }
```

The X2 decision note says "base64 inline or shared memory key," but the type only has a `String` field named `data`. For the in-process VLM path (edge-agent calling `Llm` trait directly), encoding to base64 and decoding back wastes CPU on an embedded device. For the HTTP path (C1), base64 is fine.

**Recommendation:** Use an enum: `pub enum ImageData { Base64(String), Raw(Arc&lt;[u8]&gt;) }` in `ImageRef`. This preserves zero-copy for in-process and base64 for serialization. If this is too much for first freeze, at least document in the contract comments that `data` may be a shared-memory key (not always base64), so implementations don't assume decodability.

**Modules:** B2 `Action`, B1 `SessionEvent`, B5 `TriggerEvent`, A4 `Chunk`, A1 `AsrEvent`

All evolution rules say "only add variants." Without `#[non_exhaustive]`, downstream `match` arms in consuming modules will break when a variant is added. Since these are cross-module contracts, this attribute is the Rust-idiomatic way to enforce the stated evolution rule.

**Recommendation:** Add `#[non_exhaustive]` to `Action`, `SessionEvent`, `TriggerEvent`, `Chunk`, `AsrEvent`, `GuardVerdict`, `OtaState`.

### NB-7: `B5 RuleEngine::match_event` returns `Option&lt;String&gt;` for skill_id -- should be a newtype

**Module:** B5 Trigger (workpackages.md line 383)

Returning `Option&lt;String&gt;` for a skill_id that must match a key in B6 `SkillEngine` is stringly-typed coupling. A `pub struct SkillId(pub String)` newtype shared between B5 and B6 would make the contract self-documenting and prevent accidental mixups with other string IDs (session_id, request_id, etc.).

### NB-8: A2 `Tts::synthesize_stream` takes `text: &amp;str` but real streaming TTS often receives text incrementally

**Module:** A2 Tts (workpackages.md line 93)

The current contract has a single `&amp;str` in, stream of `AudioChunk` out. This works for "one sentence at a time" (B2 sends each sentence as a separate call). ## The 6 Scrutiny Points

### (a) A4 `Llm`: mixing return-value (`chat`) and channel (`chat_stream`) -- verdict: CORRECT, with caveat

The two calling patterns are genuinely different: `chat` is used for fast-tier intent classification (B2 `ModelRouter` routes short inputs to `Fast`), which is request-response. `chat_stream` is the ReAct loop's primary path, where B2 needs to process `TextDelta` and `ToolCall` as they arrive to achieve "first sentence plays immediately."

A hypothetical unified interface (always channel) would force the intent-classification path to create a channel, spawn a reader, collect results -- overhead and complexity for a fire-and-forget call. The mixed style is the right trade-off.

**Caveat:** Per BLOCKING-2, `chat_stream` must return `Result&lt;Usage&gt;` (not `Result&lt;()&gt;`) to close the observability gap.

### (b) B2 `ReasoningStage::run_turn(ctx, cancel, tx)` 3-arg shape -- verdict: CORRECT

- `ctx: AgentContext` (owned) -- correct; the turn consumes its context, and B7 creates a fresh one per turn.
- `cancel: CancellationToken` -- correct; explicit cancellation is the Y2 decision. It is superior to drop-rx-to-stop for this case because cancellation must propagate to `chat_stream`, tool execution, and TTS simultaneously -- a single token can be cloned into all three. Drop-rx would only stop the `Action` consumer, not the upstream LLM call.
- `tx: flume::Sender&lt;Action&gt;` -- correct; B7 (the consumer) owns the `Receiver` and decides what to do with Actions (play TTS, log, etc.). The producer-consumer separation here is clean.

The `CancellationToken` is not from `tokio_util` (not specified). Recommend documenting that it is `tokio_util::sync::CancellationToken` to avoid implementers rolling their own.

### (c) A6 `Executor::run(command: &amp;str, params: Value) -&gt; Result&lt;String&gt;` stringly-typed -- verdict: ACCEPTABLE SEAM, borderline

The key insight is the division of labor: B3 `ToolHandler` owns the typed schema (`tool_def() -&gt; ToolDef` with JSON Schema); A6 `Executor` is deliberately tool-agnostic transport. The typing lives in B3, not A6. This is the "typed at the right layer" principle.

However, the return type `Result&lt;String&gt;` loses structure. If a tool returns structured JSON, the caller (B3 ToolHandler) must parse it back from a string. And `command: &amp;str` has no compile-time connection to what the Executor implementation actually supports -- a typo in a command name is a runtime error.

**Verdict:** Acceptable for v1. The alternative (generic transport with typed command enums) would couple A6 to B3's tool set, violating the stated boundary. The stringly-typed seam is the intentional cost of decoupling. Worth adding a doc comment that `command` MUST match a key in `tools.toml` (i.e., the set is finite and config-driven, not arbitrary).

### (d) B1 `get_events(offset, limit)` vs B2's "last N turns" need -- verdict: INSUFFICIENT PRIMITIVE

As detailed in NB-3, the offset/limit API requires two async calls to fetch recent events: first `event_count()`, then `get_events(count - N, N)`. This is the dominant access pattern (every single turn in B2 calls it).

Beyond the round-trip inefficiency, there is a race condition: between `event_count()` and `get_events()`, another task (B7's session timeout cleanup, or a concurrent turn) could modify the event log, making the offset stale.

**Verdict:** Add `recent_events(session_id, limit)` as a first-class method. Keep `get_events` for B8 management/audit use cases where full pagination is needed.

### (e) Streaming event enum naming: `AsrEvent`, `Chunk`, `SessionEvent` -- verdict: ACCEPTABLE, minor inconsistency

- `AsrEvent{Partial, Final}` -- domain-specific, clear.
- `Chunk{TextDelta, ToolCall}` -- LLM domain, matches OpenAI convention. The name `Chunk` is generic but acceptable since it lives in the A4 Llm module namespace (`capabilities::llm::Chunk`).
- `SessionEvent{UserInput, LlmResponse, ToolCall, ToolResult, Error}` -- memory domain events, not streaming in the same sense.

These three enums serve different purposes (ASR streaming, LLM streaming, event logging) in different modules. They are not "the same thing named differently" -- they are genuinely distinct types. The naming divergence reflects real semantic differences.

**Minor concern:** `Chunk::ToolCall` and `SessionEvent::ToolCall` share a name but mean different things (the former is an LLM output chunk, the latter is a memory log entry). This could confuse implementers who import both. In practice, they live in different module namespaces, so it is manageable. No fix needed, but a doc comment on each clarifying "this is an LLM output" vs "this is a memory record" would help.

### (f) C1 middleware-service depending on B1 `MemoryStore` + B2 `ContextBuilder` -- verdict: LAYERING VIOLATION, but pragmatically acceptable with a mitigation

The SSOT (design doc section 1.2, line 97) is explicit: "consumers are peers, depend DOWN on capabilities, do not depend on each other." B1 MemoryStore and B2 ContextBuilder are in the **orchestration layer** (edge-agent crate). If C1 depends on them, C1 depends on the orchestration layer, which is a peer consumer -- violating the stated dependency rule.

The rationale in the workpackages doc (line 488) is pragmatic: C1's `/v1/chat/completions` needs session history, and re-implementing session management in C1 would duplicate B1.

**Verdict:** This is a real layering violation against the stated architecture. The mitigation is straightforward: extract `MemoryStore` (trait + SQLite impl) and `ContextBuilder` into the `capabilities` crate (or a new `session` sub-crate of capabilities). They are not "orchestration" in the sense of ReAct loops or Guard policies -- they are stateful data access. Once extracted downward, both edge-agent and C1 can depend on them without violating the dependency rule.

If extraction is deemed too much refactoring for freeze, then at minimum: (a) document this as a known layering exception in the workpackages doc, (b) ensure C1 depends only on the `MemoryStore` and `ContextBuilder` **traits** (not the edge-agent crate), and (c) plan the extraction as a post-freeze cleanup before the crate dependency graph solidifies.

## What's Good

1. **Action model unification** (section 2 of SSOT, B2 contract): Collapsing `Mcp`/`Cli`/`Device` into a single `Tool` variant is the right call. It correctly places transport concerns in A6/B3 and keeps the LLM-facing model clean.

2. **Y1 AgentContext slimming**: Removing `vision_summary` and `device_state` from `AgentContext` and routing them through tools (B3) and state (B5) respectively is a significant decoupling win. The old `AgentContext` in `context.rs:7-17` was a grab-bag; the new one is a clean "turn input."

3. **Y2 explicit CancellationToken**: This is better than implicit channel-drop for barge-in because it propagates to all concurrent tasks (LLM stream, tool execution, TTS) simultaneously. The decision is well-reasoned.

4. **X1 frame passthrough with `Arc&lt;[u8]&gt;`**: Zero-copy frame sharing with immutable reference counting is exactly right for the hot path. The decision to encode only at the C1 HTTP boundary avoids redundant work.

5. **Two-layer tool execution** (B3 ToolHandler + A6 Executor): Clean separation of "what tool" from "how to transport." The config-driven generic handler for simple tools vs hand-written strong-typed handler for safety-critical tools is a pragmatic split.

6. **Flume channel convention**: Consistent use of `flume::Sender&lt;T&gt;` for streaming (push-based, bounded) across A1, A2, A4, B2 is a good unifying pattern. The "drop rx to stop" semantics for TTS barge-in is idiomatic.

7. **B9 PromptStore**: Centralizing all LLM-facing text (system prompts, fallbacks, fillers) with OTA hot-reload is important for a production vehicle product. This avoids the common antipattern of scattered hardcoded strings.
